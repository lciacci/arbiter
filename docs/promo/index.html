arbiter runs a reviewer, an independent second pass, and a two-voice triage vote over a git ref range. Output is two tiers — blocking and advisory — and it exits 1 on a high or critical blocking finding, so it can gate a hook. Cheap and portable, not "better than the alternative."

What it actually is

A single CLI over a git ref range. Everything it reads comes from git at a pinned SHA — never the working tree — so it is safe to point at a repo somebody else is committing to.

Cheap

The win is triage, not fan-out

Four model calls per file plus verification turns. The triage step exists to keep the blocking list short rather than long. Every run prints its own token count and cost estimate, so the claim stays checkable.

Portable

Plain Python, bare SDK client

Constructed bare, so ANTHROPIC_BASE_URL points it at any compatible gateway. No Claude Code dependency anywhere in the engine. Python 3.13+ and an API key.

Honest

It is a first pass

Measured head-to-head against a 31-agent workflow review on the same diff, arbiter found 2 of its 3 real defects and missed 8 others. It is not trying to beat the heavy option — it is trying to cost cents.

The pipeline

Independence is the design property. The second pass sees the first only as anti-redundancy context — it can add findings, never remove them. Removal is triage's job, and triage is source-blind.

1. Reviewer

Adversarial first pass over one changed file. Tuned to surface issues, not to triage them.

→

2. Second pass

An independent review that sees pass 1 only so it does not repeat it. Additive by construction.

→

3. Triage

Two source-blind voices vote KEEP / DROP / UNSURE on the merged list. They never see which pass produced a finding.

Try the rule

Both voices keep → blocking. Both drop → dropped. Anything else → advisory. Then severity decides whether the process actually fails. Pick a ballot:

Voice A — reviewer-style
Voice B — skeptic
Severity on the finding
blocking
exit 1

Severity gates as well as agreement, and it did not always. Triage votes on whether a finding is real, never on whether it is worth stopping for — so low used to reject a commit exactly as hard as critical. Measured over two runs, three of three blocking findings were cosmetic or inapplicable. A gate that cries wolf gets bypassed. Findings below high are still reported in full; they just do not fail the process. An unrecognisable severity does gate — it is model output, and the safe direction is to stop.

Exit codes

CodeMeaning
0nothing worth stopping for
1blocking findings at high or critical — reject
2could not run at all (bad ref, not a repo)
3ran, but some file failed to review — not a pass

Blocking is checked before failures, so a partial failure can never mask a confirmed blocking finding behind a softer code. 3 is distinct from 2 so a hook can tell "reviewed nine of ten files" from "arbiter never started".

Where the money actually goes

Verification is most of the spend — it triples the call count (~12 per file rather than 4) because every turn resends the conversation. What that 3× buys is filtering, not volume: the same number of findings, but roughly three times as many dropped by triage.

Prompt caching takes most of the resend cost back. The finders' system prompt and tool definitions cache together, and so does the verification transcript, so turn N reads turns 1..N−1 instead of re-paying for them. Measured end-to-end on one 230-line Python file at --jobs 1: 6 calls, 75,552 prompt tokens, 50% served from cache, $0.17 — against $0.24 at full input rate.

Triage is deliberately not cached, and the number is why: its prefix measures 1017 and 1024 tokens against a 1024-token minimum. A breakpoint there would silently cache nothing half the time — and a marker that caches nothing is worse than no marker, because it reads as done.

Verification, and the security boundary

The reviewer and second pass can run read-only inspections before reporting a claim — check what a diff really contains, grep for a symbol's other uses, read a file at the pinned ref. On by default, and the single change that most improved finding quality: on its first run with any inspection tool at all, it found two allowlist bypasses in its own newly-written security code.

Replaced

A command string with an allowlist

An earlier version took a command and allowlisted argv[0]. An independent review found five confirmed ways through it — python3 -c (a whole interpreter), a repo-supplied binary whose basename matched, attached-value options like sort -o/etc/evil, awk 'BEGIN{system()}', and sed -i.bak writing to the tree. The first patch was the wrong shape too: seven of eight exploits still worked, because -i.bak is not -i.

Current

Typed tools, argv built here

The model supplies parameters — read_file(path, ref), search(pattern, path, ref), git_diff(...), git_log(...) — and the argument vector is constructed in-process. No position where model input becomes a binary or a flag. Paths and refs are rejected if absolute, containing .., or beginning with -; patterns go through -e so they cannot be read as options.

A general-purpose Unix tool is a language, and you cannot enumerate the dangerous sentences in a language.

This boundary is young. The typed-tool rewrite has a handful of live runs behind it, none of them adversarial, and the current design has never been independently reviewed at all. The argument for it is that it removes the category — model input never reaches argv, no interpreter, no free text to a shell — not that it has been proven in use. The model chooses what to inspect after reading a diff, and a diff can contain text written by someone else, so this is a prompt-injection surface. Reviewing a change from someone you do not trust: use --no-verify, or run it in a container.

Using it

Reviews .py .sh .bash .zsh .ts .tsx .js .jsx .sql by default, plus any extensionless file starting with a shebang; --ext sets the list and --path overrides scope outright. Whatever it declines to open is named in the report. Uncommitted work is never reviewed — everything comes from git.

# Python 3.13+, ANTHROPIC_API_KEY in the environment or a .env
git clone https://github.com/lciacci/arbiter && cd arbiter
uv sync
uv run arbiter --help
# Review the current branch against main
arbiter --base main

# Review another repo from anywhere
arbiter --repo ~/code/thing --base main

# A specific commit range, written to markdown
arbiter --base HEAD~3 --head HEAD --out review.md

# Machine-readable: findings plus the usage record
arbiter --json
# --path is the lever. Repeatable; prefixes or globs.
arbiter --path src/arbiter --path 'tests/*.py'

# Roughly halves a run. Also: use this for code you do not trust.
arbiter --no-verify

# Cheaper and noisier: no triage, everything lands advisory
arbiter --no-triage
# The exit codes are designed for this — but read the note below first.
arbiter --base "$(git merge-base HEAD origin/main)" || exit 1

Not wired up as a hook here, deliberately. At 1–2 minutes and $0.79–$2.74 a run it is too slow and too expensive to fire automatically, and since severity started gating the exit code, the exit-1 path has not triggered on real code once — so its precision at the tier that gates is unmeasured. Run it by hand until that is known.

What the numbers do and don't say

The pattern comes from pr-arbiter, a research POC measured against a 20-PR corpus of planted bugs. Read the result honestly before trusting this tool more than it has earned.

Phase 1 — code review

7/8 vs 6/8 criticals

The multi-agent configuration caught 7 of 8 criticals against 6 of 8 for the best single-agent reviewer, at comparable precision — on one seed.

Phase 2 — code generation

The effect largely vanished

Ported to code generation and re-run across 3 seeds, multi-agent scored 34/39 against 32/39 for solo — same direction, roughly half the effect size the single-seed pilot suggested.

So: the architecture is directionally useful and thinly evidenced. The reason to run arbiter is cost and portability, not a claim that it out-finds the alternatives. All of it measured on Sonnet 4.6.

Why it missed them — not context. Every missed defect was inside one file, most within twenty lines of itself. The gap was that the workflow's agents ran git in scratch repos and introspected the installed SDK, while arbiter's could only reason from text. That is what produced the verification tooling. A head-to-head since verification landed has never been run.

Six blocking/advisory findings from real runs on three repos, each verified by hand before acting. The pattern that held every time: the finder is better at locating than at concluding.

🎯
tessera — real, fixed
A found-but-crashing script set its found-flag on the same line as the interpreter call, suppressing the degraded report the change existed to emit. In code written an hour earlier to close a silent-failure bug, which its author had already tested hard.
🎯
tessera — the jq-absent fallback
A glob matched *'"source"'*'"startup"'*, which does not require startup to be source's own value. Verified: a crafted payload triggers the re-anchor the guard exists to prevent. Found in shell, on the first foreign-repo try, for $0.73.
🌓
conclave — observation right, consequence wrong
It spotted a watchdog subshell leaking its sleep child, then claimed the orphan goes on to fake an rc=137 on the next invocation. It cannot — killing the subshell kills the sequence. Verified by running a reduced copy. The real defect is a leaked sleep per task: cosmetic.
🌓
tessera — right instinct, wrong justification, taken anyway
It claimed a per-project tally keyed by directory name would merge same-named projects. The premise is false — the discovery glob is single-parent, so names are unique by construction. Taken regardless, for a reason it never gave: a merged counter would hold a counting predicate quiet, and it should not depend on a property of a different function.
💤
conclave — inert
env -C called non-portable. True only for macOS <13; works on the actual machine and on GNU coreutils ≥8.28.
💤
tessera — inert
Restore scripts not chmod +x'd, argued to silently skip an install via an [ -x ] probe. The probe is [ -f ] and the file runs as python3 <path>; the exec bit is irrelevant.

Verifying the repro before acting caught the wrong consequence every time it appeared. That is the recommended way to read arbiter's output: trust the location, check the story.

Where it loses

Known limits. The one that used to head this list — a review narrower than it claimed — is fixed; it is kept here, marked, because deleting it would be the same dishonesty in a different direction.

✅
FIXED — extensionless files were silently skipped
is_reviewable() filtered on suffix, so a shebang script with no extension was dropped while the output still read "N file(s) reviewed · 0 blocking", and --path could not rescue it because the filter ran first. Two runs against tessera reviewed the tests and skipped the code. All three parts have landed: skipped files are named in the report, --path runs first and is authoritative, and extensionless files are picked up by shebang. Still unconfirmed on the branch that exposed it — the fix is unit-tested, not yet re-run against the original diff.
📄
Per-file review
Agents see one file at a time and cannot reason across files in the same change. Worth knowing, but measurably not the binding constraint: every defect arbiter missed in the head-to-head sat inside a single file.
💸
No incremental caching and no cost cap
A large branch can be expensive and nothing stops it mid-run. --path is the lever.
🧪
False positives on request-derived input — partially addressed
The reviewer now has to trace where an attacker-controlled value actually enters before reporting an injection-class finding. Whether that holds up outside this repo is untested.
⚖️
Not a substitute for a heavier review
2 of 3 real defects found, 8 missed, against a 31-agent workflow on the same diff. It is a cheap first pass and it is honest about being one. Two independent looks at the same security boundary produced six exploits between them, one apiece missed by the other — that is an argument for running both, not for picking one.

Fail-open — the recurring defect

Not one bug, a pattern — five instances, several written by whoever had just fixed the previous one. Each was defensive in intent. A review tool's worst failure is not a wrong finding; it is a confident silence over code it never looked at.

When adding a fallback here, ask what a gate will conclude from it. If the answer is "pass", it is wrong. And any narrowing of scope must appear in the output, or the report is a false green.
